llms.txt y slopsquatting: tu docs invita al agente al paquete falso

En 2026 mucha empresa publica llms.txt para guiar a agentes de código. Si ese archivo apunta a un paquete o dominio que nadie registró, un atacante lo reclama y el agente lo instala como si fuera oficial.

El llms.txt nació para ayudar: un archivo en la raíz del sitio que resume APIs, SDKs y comandos de instalación para que un agente de código no alucine. El problema de 2026 es el modelo de confianza: el agente trata esa documentación como verdad y ejecuta lo que dice —incluido un npm install o un pip install— sin comprobar que el paquete exista, sea tuyo o haya sido revisado.

Investigaciones recientes de la Cloud Security Alliance y escaneos sobre miles de dominios corporativos mostraron el patrón: una fracción medible de archivos llms.txt publica nombres de paquetes o dominios nunca registrados. Quien reclama ese nombre y sube un paquete “de teléfono a casa” puede ver cómo Claude, Codex u otros agentes lo instalan dentro de la red, a veces en minutos. No parece malware clásico: entra por el gestor de paquetes que ya confías y por la docs que tú mismo publicaste.

Qué es (y qué no es)

El slopsquatting clásico aprovecha nombres que el modelo inventa. La variante vía llms.txt invierte la superficie: el atacante lee tu archivo público, anota el nombre exacto que tu empresa invita a instalar y que aún no existe, y lo registra. El agente no “alucinó” el paquete; obedeció tu documentación.

No sustituye al gateway MCP ni a las identidades no humanas: aquí el vector es la cadena de suministro del propio asistente de desarrollo. Tampoco es “el modelo es malo”: es un fallo de verificación entre docs, registro y ejecución.

Por qué duele en LatAm

Agentes de código ya en el día a día. Muchos equipos en Lima, Bogotá o Ciudad de México dejan que el copiloto instale dependencias “como dice el README del proveedor”. Si ese README o el llms.txt apunta a un nombre libre, el riesgo viaja con el flujo normal de trabajo.

Docs publicadas con prisa. Marketing o producto publican guías para agentes sin el mismo rigor que un release de software: ejemplos inventados, SDKs “próximos” o typos que nadie reclamó en npm/PyPI.

Controles de endpoint ciegos. El agente usa el mismo npm/pip aprobado. El EDR ve una instalación legítima; no ve que el dueño del paquete cambió esta mañana.

Cómo blindarlo sin teatro

Audita tu propio llms.txt. Lista cada paquete, URL y comando de instalación. Verifica en el registro oficial que el nombre existe, que la cuenta publicadora es tuya o del vendor, y que hay historial (no un paquete de ayer con cero versiones previas).

Registra antes de documentar. Si vas a mencionar un SDK futuro, reserva el nombre en el registro o no lo publiques. Un nombre libre en docs públicas es una invitación abierta.

Pin y lockfile. El agente no debe “resolver lo último”: versiones fijas, hashes y lockfiles revisados. Prohíbe instalación desde URLs crudas o registros no allowlisted en el sandbox del piloto.

Política en el runtime del agente. Antes de ejecutar un install, exige allowlist de paquetes o revisión humana. El mismo criterio de human-in-the-loop para lo irreversible aplica a “bajar código de internet”.

Prueba roja. En staging, publica un llms.txt de prueba con un nombre inventado no registrado. Si el agente lo intenta instalar, tu pipeline todavía confía en docs como si fueran firmadas.

Checklist de esta semana

  • Abre el llms.txt (y READMEs que citan agentes) de tu producto o de vendors críticos; anota cada nombre de paquete y dominio.
  • Comprueba en npm, PyPI u otro registro: existencia, dueño, fecha de primera publicación y si coincide con el vendor.
  • Registra o retira nombres libres; corrige typos antes de que alguien más los reclame.
  • En el entorno del agente de código: solo registros allowlisted, lockfiles y sin install desde URL arbitraria.
  • Ensayo: nombre inventado en docs de staging — documenta si el agente intentó instalarlo y cierra el hueco.

Criterio GAPATIC

Publicar llms.txt sin verificar la cadena de suministro convierte tu documentación en vector de instalación. Primero nombres reales y tuyos, versiones fijas y un freno antes del install; después más guías para agentes. Si un archivo en tu dominio puede hacer que el copiloto baje un paquete que nadie de tu empresa publicó, todavía no tienes onboarding para agentes: tienes una puerta lateral firmada por ti.
