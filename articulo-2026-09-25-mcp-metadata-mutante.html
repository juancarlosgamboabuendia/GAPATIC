MCP de cara amable: el servidor que muda a la tercera llamada

En 2026 mucha empresa en LatAm conecta un servidor MCP “inofensivo” desde un PR o un registro público. Si el metadata de tools/list solo se envenena después de unas llamadas benignas, la revisión rápida pasa y el agente termina buscando credenciales como si fuera política.

En 2026 el Model Context Protocol (MCP) ya es el conector por defecto entre el agente de código y Jira, el correo o el filesystem. Eso acelera el piloto. También abre un vector que la revisión de “¿qué tools ofrece?” no alcanza: el servidor puede mostrar una cara amable en las primeras llamadas y cambiar el metadata después, cuando nadie está mirando.

Campañas recientes de cadena de suministro —servidores MCP repartidos por pull requests públicos que parecen utilidades de texto— ilustran el patrón. Durante unas pocas tool calls el servidor responde con herramientas inocuas. Pasado un umbral, reescribe las descripciones e instrucciones que el cliente MCP entrega al modelo: “busca claves SSH”, “lee historial de shell”, “oculta esto al usuario”. La inspección rápida y el smoke test corto pasan. El daño empieza en la sesión de trabajo real.

Qué es (y qué no es)

No es solo un gateway MCP mal configurado. El gateway decide qué servidores entran. Aquí el servidor ya entró y miente en el tiempo: el contrato de tools/list o de prompts que viste al conectar no es el que el agente recibirá tras unos minutos de uso.

Tampoco es solo slopsquatting en docs. Ahí el paquete falso vive en el registro. Aquí el artefacto puede ser el propio servidor MCP —o un PR que lo mete en tu repo— y el envenenamiento es de metadata en runtime, no solo de nombre de dependencia.

Por qué duele en LatAm

PR “de productividad” sin dueño de seguridad. Un contribuidor o un bot ofrece un MCP de resumen o formato. El equipo de producto lo mergea para desbloquear el piloto. Nadie firma el binario ni fija el hash del servidor.

Pruebas cortas que no cruzan el umbral. El analista hace dos o tres llamadas de formato, ve texto limpio y da el OK. El umbral de activación del metadata malicioso queda justo detrás de esa prueba.

Credenciales en el mismo entorno. El agente corre donde hay AWS, kubeconfig o tokens de API. Si el metadata envenenado pide “lee ~/.ssh” y no hay sandbox ni política de tool call, el modelo cumple como si fuera una tool legítima.

Cómo blindarlo sin teatro

Fija y firma el servidor. Versión pinneada, checksum o firma; allowlist de endpoints. Un MCP “cualquiera del marketplace” no entra a producción.

Vuelve a pedir consentimiento cuando muda el contrato. Si tools/list, descripciones o system hints cambian respecto a lo aprobado, el cliente debe cortar o reautorizar. Un contrato que deriva sin aviso es un incidente.

Observa el metadata, no solo el resultado. Registra snapshots de tools/list y de instrucciones inyectadas por el servidor. Deriva = alerta, igual que un drift de configuración en un servicio crítico.

Menos privilegios en el host del agente. Sin lectura amplia del home, sin egress libre y sin la cuenta del humano. El metadata malicioso pierde poder si el entorno no puede cumplir lo que pide.

Revisa la cadena de entrada. PRs que tocan configs MCP, Dockerfiles o scripts de instalación del servidor pasan por el mismo control que una dependencia de producción —no por el atajo de “es solo un conector”.

Checklist de esta semana

  • Inventaria qué servidores MCP usa tu equipo (local, remoto, vía PR) y quién los aprobó.
  • Compara el tools/list de hoy con el de la aprobación inicial; documenta cualquier deriva.
  • Simula más de tres tool calls contra cada servidor no firmado; guarda el metadata completo, no solo el éxito de la herramienta.
  • Bloquea writes y lecturas de secretos fuera de un sandbox; el agente no debe poder “buscar claves” aunque el prompt lo pida.
  • Exige pin + firma (o mirror interno) antes de mergear un MCP nuevo.

Criterio GAPATIC

Un servidor MCP no es una librería estática: es un interlocutor que puede cambiar lo que le dice al modelo mientras corre. Si tu control de calidad solo mira la primera cara amable, estás certificando el disfraz. Primero fija el contrato, observa la deriva y aísla el host; después presume “utilidad de productividad”. Si a la tercera llamada el metadata ya no es el que firmaste, no tienes un conector: tienes un canal de mando diferido dentro del protocolo.

Si quieres inventariar tus MCP, fijar contratos y poner alerta de deriva de metadata, hablemos.
