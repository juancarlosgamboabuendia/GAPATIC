Schema drift de tools: el contrato que el agente ya no conoce

En 2026 mucha empresa en LatAm fija el prompt del agente y deja que el esquema de tools “se descubra” en runtime. Si el ERP, el CRM o un MCP cambian un campo obligatorio y nadie versiona el contrato, el piloto sigue vivo pero llama a un mundo que ya no existe.

El demo del agente suele fallar por el modelo. En producción, el fallo silencioso es otro: el contrato de las tools se movió y el agente sigue llamando con el mapa de la semana pasada. El ERP renombró un campo, el CRM volvió obligatorio un atributo, el servidor MCP cambió la descripción o el enum de una tool. El prompt no cambió. La corrida “pasa”. El resultado, no.

Eso es schema drift de tools: la definición que el modelo ve (nombre, descripción, JSON Schema de entrada/salida, efectos laterales) deja de coincidir con lo que el ejecutor o el sistema de destino realmente aceptan. No es un bug del LLM. Es un problema de versionado que muchas empresas en LatAm tratan como detalle de integración.

Qué se rompe cuando el contrato se mueve

Un agente no “entiende” tu API: llama lo que le declaras. Si en runtime descubres el esquema actual sin anclarlo a una versión, cada deploy del backend o del conector MCP puede alterar lo que el modelo cree que puede hacer. Los síntomas típicos:

  • Llamadas que antes funcionaban y ahora fallan por campos nuevos requeridos o tipos cambiados.
  • Llamadas que “tienen éxito” pero escriben en el campo equivocado porque el nombre o el significado mutó.
  • Descripciones de tools que empujan al modelo a un uso que la política ya no permite (o al revés: ocultan un riesgo nuevo).
  • Tests del piloto verdes porque fijaron fixtures viejos, no el contrato vivo.

Esto se parece al MCP de metadata mutante, pero el vector no tiene que ser un atacante. Basta un release de tu propio equipo o de un SaaS sin aviso semántico.

Por qué duele en LatAm

Integraciones frágiles y multi-vendor. Mid-market en la región encadena ERP local, CRM cloud, WhatsApp Business y un MCP “rápido”. Cada pieza tiene su ciclo de release. El agente es el pegamento; el pegamento no tiene changelog.

Descubrimiento dinámico sin pin. Frameworks y gateways prometen “tools/list siempre fresco”. Útil en desarrollo. En operación, fresco sin fingerprint es drift continuo: el agente de hoy no es el que evaluaste el viernes.

Pocas pruebas de contrato en el camino del agente. Hay unit tests del adaptador y a veces evals de prompt. Casi nadie tiene un diff de esquema (breaking vs compatible) atado al deploy del agente, ni fixtures de request/response reales contra el contrato versionado.

Cómo blindarlo sin teatro

Un contrato versionado por tool. Nombre, descripción, schema de entrada/salida, ejemplos, efectos laterales, permisos y versión del adaptador. Calcula un fingerprint estable. Ese fingerprint es parte del release del agente, no un detalle de runtime.

Genera el schema que ve el modelo desde ese contrato. No copies a mano en el prompt una versión y en el código otra. Una sola fuente; el modelo y el ejecutor salen del mismo artefacto.

Clasifica cambios: compatible vs breaking. Campo opcional nuevo suele ser compatible. Renombrar, endurecer tipos o agregar required es breaking. Breaking exige bump de versión, re-evaluación del agente y, si aplica, ventana de dual-read.

Falla cerrado si el runtime ve otro fingerprint. Si el servidor MCP o el gateway sirven un schema distinto al del release, no “adaptes en caliente”: pausa la tool o el agente. Mejor un error visible que una escritura silenciosa al lugar equivocado.

CI con ejemplos reales. Diff estructural del schema + tests con payloads que pasaban ayer. Incluye al menos un caso que un schema laxo aceptaría y tu aserción semántica rechaza. Amárralo al mismo pipeline que despliega el agente.

Dueño del contrato. Cada tool tiene un responsable (producto o plataforma), no “el equipo del agente”. El dueño del ERP firma el cambio; el dueño del agente decide si el release puede salir.

Checklist de esta semana

  • Lista las tools que tu agente puede llamar y anota de dónde sale cada schema (estático, MCP, OpenAPI generado).
  • Asigna versión y fingerprint a las tres tools de mayor impacto (ERP, CRM, pagos o identidad).
  • Compara el schema del release actual con el de runtime en staging; documenta cualquier diff.
  • Añade un job de CI que falle si el fingerprint del contrato no coincide con el empaquetado en el agente.
  • Define política: cambio breaking de tool = redeploy del agente + smoke de las tareas críticas.
  • Simula un required nuevo en una tool de escritura y verifica que el agente no “invente” valores para seguir.

Criterio GAPATIC

Un agente estable no es solo un buen prompt: es un release atado a contratos de tools. En 2026, descubrir el schema en caliente sin versión es aceptar que el piloto cambie de comportamiento cada vez que un sistema de atrás se mueva. Primero contrato versionado, fingerprint y fail-closed; después presume que “la integración sigue igual”.
