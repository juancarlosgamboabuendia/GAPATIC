SSRF por tools: el agente que abre tu red interna

En 2026 mucha empresa en LatAm le da al agente una tool HTTP “para consultar APIs”. Si esa tool acepta cualquier URL sin allowlist ni bloqueo de rangos privados, una inyección o un documento malicioso convierte al agente en un proxy hacia tu red interna: metadata cloud, admin panels y servicios que nunca debieron verse desde internet.

El equipo pide una tool “fetch” o “http_get” para que el agente consulte APIs, lea un webhook o “abra un enlace del correo”. Se conecta en una tarde. Lo que casi nadie define es quién elige la URL y hacia dónde puede salir esa request.

Eso es el riesgo del SSRF por tools: Server-Side Request Forgery clásico, pero disparado por un agente que confía en contenido no confiable —prompt, email, PDF, chunk RAG o salida de otra tool— y lo convierte en destino HTTP. No hace falta un exploit de cero día. Basta una tool útil con permisos de red amplios y sin allowlist.

Qué es SSRF vía agente

En el SSRF tradicional, la aplicación server-side pide una URL que controla el atacante. Con agentes, el patrón es el mismo: la tool de fetch/HTTP/webhook hace la request desde tu infraestructura (VPC, on-prem, hop con acceso a la red interna). El modelo solo arma el argumento; la tool ejecuta.

Destinos típicos que aparecen cuando no hay filtro:

  • 169.254.169.254 y variantes de metadata cloud (credenciales temporales, identidad de instancia).
  • localhost, 127.0.0.1, ::1 — paneles de admin, agentes locales, bases en el mismo host.
  • Rangos RFC1918 (10.x, 172.16–31.x, 192.168.x) y link-local.
  • DNS rebinding: un hostname “público” que después resuelve a IP privada.
  • Redirects HTTP: la tool sigue un 302 hacia un destino interno que nunca estuvo en la allowlist.

Si el contenido recuperado (o el prompt) puede elegir la URL final sin validación fuera del modelo, el agente deja de ser un copiloto: es un proxy autenticado hacia tu red.

Por qué duele en LatAm

Agentes pegados al ERP y a VPCs pequeñas. Mid-market y operaciones regionales suelen poner el agente en la misma red (o VPN) que el ERP, el CRM o el file server “para que sea útil”. Una sola tool HTTP con salida libre ve lo que internet no debería ver.

Una tool “útil” con permisos amplios. Se entrega fetch genérico porque “mañana puede hacer falta otra API”. No hay dueño de la allowlist ni revisión de esquemas privados. El piloto pasa a producción con la misma tool del demo.

Poca separación red/agente. El hop del agente, el worker de tools y el servicio interno comparten segmento. No hay egress control ni identidad de tool con alcance mínimo. Cuando llega un documento malicioso al RAG o un correo al inbox del agente, la red ya está al alcance de un solo tool call.

Cómo blindarlo sin teatro

Allowlist de hosts y esquemas. Solo HTTPS (o el esquema que apruebes) hacia hosts nombrados. Nada de “cualquier URL que el modelo invente”. La validación corre en código de la tool, no en el system prompt.

Bloquear RFC1918, link-local y metadata. Resuelve el hostname, comprueba la IP final y rechaza privados, loopback y 169.254.0.0/16 (y equivalentes IPv6). Hazlo otra vez después de cada redirect. DNS rebinding se mitiga resolviendo y fijando la IP (o revalidando en cada hop).

No seguir redirects a destinos no allowlisted. O desactiva redirects, o revalida el Location con la misma política. Un 302 a metadata no es un “detalle del cliente HTTP”.

Credenciales de tool con alcance mínimo. La identidad con la que sale el fetch no debe ser la del ERP ni la del admin. Scope corto, rotación, y preferible un hop de egress que solo hable con APIs aprobadas.

Política: el contenido no elige la URL final sin validación fuera del modelo. Si un PDF o un chunk RAG sugiere un enlace, ese string pasa por el mismo validador que un parámetro de API. El modelo propone; la tool decide si sale.

Logs de cada request. Host (y IP resuelta), status, bytes, tool_id, tenant y correlación con el turno del agente. Sin eso no hay incidente que investigar: solo “el agente abrió algo”.

Checklist de esta semana

  • Lista todas las tools que hacen HTTP/fetch/webhook y anota quién puede influir en la URL (prompt, email, RAG, otra tool).
  • Prueba desde el sandbox: pide a la tool http://169.254.169.254/, http://127.0.0.1/ y un host de tu red interna; documenta si responde.
  • Implementa allowlist de hosts + bloqueo de rangos privados/link-local/metadata en el código de la tool.
  • Desactiva redirects o revalida el destino en cada hop.
  • Revisa qué credenciales usa el hop del agente para salir a red; reduce alcance.
  • Activa log estructurado (host, IP, status, bytes) y revisa 48 h de tráfico anómalo a privados.

Criterio GAPATIC

Una tool HTTP sin allowlist no es “integración ágil”: es egress no gobernado con cara de copiloto. En 2026, darle al agente capacidad de abrir URLs controladas por contenido no confiable —sin bloquear red interna ni metadata— es abrir un proxy hacia lo que internet nunca debió ver. Primero allowlist, bloqueo de privados y logs; después presume que el fetch es seguro.

Si quieres diseñar la allowlist de tools HTTP, el bloqueo de SSRF y el egress de tu agente —sin dejar la red interna al alcance de un PDF— hablemos.
